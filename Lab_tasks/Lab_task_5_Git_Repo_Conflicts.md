# Лабораторные задачи: Создание и ведение репозитория, разрешение конфликтов, работа с удалёнными репозиториями

**Цель:** на небольшом учебном проекте освоить полный цикл работы с Git: инициализация репозитория, ветвление, моделирование и разрешение merge-конфликта, взаимодействие с удалённым репозиторием (GitHub / GitLab) и фиксация шагов в документации.

---

## Требования к реализации

Каждый студент получает **одну** задачу (номер задачи соответствует номеру в журнале). Нужно выполнить **полный сценарий** по своей постановке:

1. **Локальный репозиторий** — создать учебный мини-проект по теме задачи, сделать начальные коммиты на основной ветке (`main` / `master`).
2. **Ветвление** — создать как минимум две рабочие ветки, внести в них **противоречивые** изменения в один и тот же файл (или файлы), чтобы при слиянии возник merge-конфликт.
3. **Разрешение конфликта** — смоделировать конфликт (через `merge` или `rebase` — указать, что использовали), разрешить его осознанно, зафиксировать итог коммитом.
4. **Удалённый репозиторий** — опубликовать проект на GitHub или GitLab, связать remote, выполнить `push` / `pull` (и при необходимости Pull/Merge Request).
5. **Документация** — в `README.md` пошагово описать все команды и решения (включая фрагмент конфликтных маркеров и как их сняли).

### Общие правила

- Язык мини-проекта на выбор: Python, JavaScript/TypeScript, Java, C#, Markdown-сайт и т.п. Достаточно **небольшого** объёма (несколько файлов), чтобы конфликт был наглядным.
- Конфликт должен быть **реальным**: две ветки меняют одни и те же строки по-разному (не «пустой» конфликт и не конфликт только из‑за переименования без содержательного расхождения).
- В истории коммитов должно быть видно: начальная работа → работа в ветках → конфликт → разрешение → синхронизация с remote.
- Сообщения коммитов — осмысленные, на русском или английском (единый стиль внутри репозитория).
- Не удалять историю после разрешения конфликта «переписыванием ради красоты», если это скрывает сам конфликт; допустим обычный merge-commit или корректно оформленный rebase — с пояснением в README.
- Репозиторий **публичный** (или доступный по ссылке без запроса доступа).

### Формат сдачи

Ответ студента — **ссылка** на открытый репозиторий (GitLab / GitHub), в котором есть:

| Файл / элемент | Содержание |
|----------------|------------|
| Исходники мини-проекта | Код/контент по теме задачи |
| История веток и коммитов | Видны ветки, конфликт и его разрешение |
| Remote (origin) | Проект залит на GitHub/GitLab |
| `README.md` | Постановка + **фамилия и инициалы** + пошаговый отчёт (команды, сценарий конфликта, скриншоты по желанию) |

Пример шапки `README.md`:

```markdown
# Задача N: <название>

**Студент:** Иванов И.И.

<сюда скопирована постановка задачи из этого файла>

## Ход работы
...
```

Рекомендуемые разделы отчёта в `README.md`: структура репозитория; список веток; сценарий конфликта (что меняли в каждой ветке); как разрешили; команды для remote; ссылка на репозиторий.

Ссылка на репозиторий отправляется преподавателю.

## Список задач

### 1. Чек-лист подготовки к экзамену

Мини-приложение или Markdown-список тем к экзамену. В ветке `add-topics` добавьте новые пункты в середину списка; в ветке `reorder` измените порядок и формулировки тех же пунктов. Слейте, разрешите конфликт в файле списка, запушьте на remote.

---

### 2. Меню студенческой столовой на неделю

Файл меню (JSON/YAML/Markdown). Ветка `update-prices` меняет цены блюд; ветка `rename-dishes` переименовывает те же позиции. Создайте конфликт в одном файле меню, разрешите, сохраните согласованное меню в `main`, опубликуйте репозиторий.

---

### 3. Конфигурация учебного бота-напоминалки

Файл `config` (например, JSON) с текстом напоминаний и расписанием. Ветка `morning-schedule` правит утренние слоты и тексты; ветка `evening-texts` меняет те же ключи под вечерний режим. Разрешите конфликт конфигурации и выложите на GitHub/GitLab.

---

### 4. Страница «Расписание кружков» (статический HTML/Markdown)

Две ветки правят один и тот же блок расписания: одна добавляет новые кружки в таблицу, другая меняет время и аудитории уже существующих строк. Смоделируйте merge-конфликт, исправьте таблицу, запушьте результат.

---

### 5. Список литературы к курсовой

Файл `references.md` / `bib`. Ветка `apa-style` приводит записи к одному стилю оформления; ветка `add-sources` добавляет источники и правит те же строки. Разрешите конфликт списка литературы, задокументируйте шаги.

---

### 6. Мини-каталог вузовских мероприятий

Данные о мероприятиях (CSV или JSON). Ветка `fix-dates` сдвигает даты; ветка `fix-venues` меняет места проведения тех же записей. Конфликт при слиянии → разрешение → remote.

---

### 7. README шаблона лабораторного отчёта

Общий шаблон отчёта. Ветка `strict-structure` ужесточает обязательные разделы; ветка `student-friendly` упрощает формулировки тех же разделов. Разрешите конфликт шаблона и опубликуйте итоговую версию.

---

### 8. Игровой баланс учебной текстовой RPG

Файл параметров персонажа/врагов. Ветка `nerf-enemies` снижает характеристики; ветка `buff-player` одновременно меняет связанные строки баланса. Создайте и разрешите конфликт, сохраните согласованный баланс.

---

### 9. Политика CONTRIBUTING для студенческой команды

Файл правил вклада в репозиторий. Две ветки предлагают разные правила именования веток и формата commit message в одних и тех же абзацах. Слейте с конфликтом, выберите итоговые правила, запушьте.

---

### 10. Прайс мини-типографии при вузе

Прайс-лист услуг. Ветка `promo-discount` вносит скидочные цены; ветка `new-services` добавляет услуги и правит соседние строки прайса. Разрешите конфликт и выложите репозиторий.

---

### 11. Словарь терминов курса «Проектирование и программирование»

Глоссарий в Markdown. Ветка `expand-defs` расширяет определения; ветка `add-terms` вставляет новые термины между существующими. Конфликт в середине файла → разрешение → remote.

---

### 12. Настройки линтера / форматтера учебного проекта

Конфиг ESLint/Prettier/ruff/editorconfig (на выбор). Ветка `stricter-rules` усиливает правила; ветка `team-exceptions` ослабляет или меняет те же опции. Разрешите конфликт конфига, кратко обоснуйте итог в README.

---

### 13. Скрипт генерации бейджей участия в хакатоне

Скрипт + файл данных участников. Две ветки правят шаблон текста бейджа и поля в данных (одни и те же строки). Слейте с конфликтом, почините генерацию, опубликуйте.

---

### 14. Карта этажей учебного корпуса (текстовая схема)

ASCII/Markdown-схема помещений. Ветка `renumber-rooms` меняет нумерацию; ветка `add-labs` добавляет лаборатории, затрагивая те же фрагменты схемы. Разрешите конфликт схемы.

---

### 15. Чек-лист деплоя учебного сайта кафедры

Файл `deploy-checklist.md`. Ветка `add-security-steps` добавляет пункты безопасности; ветка `simplify-flow` сокращает и переписывает те же шаги. Конфликт → разрешение → push на remote.

---

### 16. Мини-API «Книги библиотеки» (заглушки маршрутов)

Файл маршрутов/хендлеров. Ветка `feature-search` меняет обработчик поиска; ветка `feature-filter` параллельно правит тот же файл (сигнатуры/пути). Разрешите конфликт кода, убедитесь что оба сценария учтены.

---

### 17. Таблица коэффициентов стипендии

Таблица правил начислений. Ветка `update-thresholds` меняет пороги баллов; ветка `update-amounts` меняет суммы в тех же строках. Слейте, согласуйте таблицу, опубликуйте репозиторий.

---

### 18. Локализация интерфейса «Запись в спортзал»

Файлы строк `ru` (и при желании `en`). Две ветки правят одни и те же ключи перевода по-разному. Разрешите конфликт локализации, зафиксируйте итоговые формулировки.

---

### 19. План релиза студенческого пет-проекта

`CHANGELOG` / `ROADMAP`. Ветка `release-1.1` описывает один набор изменений; ветка `hotfix-notes` правит те же разделы под срочный фикс. Создайте merge-конфликт заметок о релизе и разрешите его.

---

### 20. Конфиг Docker Compose для учебной БД

`docker-compose.yml` (или аналог). Ветка `add-redis` добавляет сервис и меняет сеть/переменные; ветка `tune-postgres` правит те же фрагменты файла под другую конфигурацию Postgres. Разрешите конфликт compose-файла.

---

### 21. Анкета обратной связи после лабораторной

Форма (HTML или описание полей в Markdown/JSON Schema). Ветка `more-questions` добавляет вопросы; ветка `rephrase` меняет формулировки пересекающихся полей. Конфликт → разрешение → remote.

---

### 22. Набор SQL-миграций учебного сервиса «Очередь в деканат»

Две ветки добавляют миграции, затрагивающие одну таблицу по-разному (имена столбцов/ограничения в одном файле или в соседних с конфликтным слиянием истории). Разрешите конфликт миграций осмысленно, опишите выбранную схему в README.

---

### 23. Тема оформления статического блога (CSS)

Общий CSS-файл. Ветка `dark-theme` меняет цвета и отступы; ветка `compact-layout` правит те же селекторы под компактную вёрстку. Разрешите конфликт стилей, покажите итоговый вид (скрином или кратким описанием).

---

### 24. Список зависимостей учебного CLI-инструмента

`requirements.txt` / `package.json` / `csproj` — на выбор. Ветка `upgrade-libs` поднимает версии; ветка `add-devtools` добавляет пакеты и попутно меняет те же строки. Разрешите конфликт манифеста зависимостей.

---

### 25. Сценарии приёмочных тестов (Gherkin или Markdown)

Файл сценариев. Ветка `happy-path` уточняет основные шаги; ветка `edge-cases` меняет те же сценарии под граничные случаи. Слейте с конфликтом, соберите единый набор тестов.

---

### 26. Политика `.gitignore` монорепозитория курсовых

Файл `.gitignore`. Ветка `ignore-ides` добавляет правила для IDE; ветка `ignore-build` меняет пересекающиеся шаблоны игнорирования. Разрешите конфликт, проверьте что нужные учебные файлы не потерялись.

---

### 27. Документация REST-эндпоинтов «Электронный пропуска»

OpenAPI/Swagger-фрагмент или Markdown API. Две ветки правят описание одного и того же эндпоинта (параметры, ответы). Разрешите конфликт спецификации и запушьте.

---

### 28. Игровое поле «Крестики-нолики» (конфиг карты / стартовая позиция)

Файл начального состояния поля или правил. Ветка `variant-3x3` и ветка `variant-custom` по-разному задают размер/стартовые клетки в одних и тех же строках. Создайте конфликт, выберите итоговый вариант правил, оформите полный отчёт и remote.

---

## Критерии проверки (ориентир)

| Критерий | Что смотрят |
|----------|-------------|
| Репозиторий | Есть локальная история коммитов и связь с удалённым origin |
| Ветвление | ≥ 2 рабочих ветки с осмысленными изменениями по теме задачи |
| Конфликт | Наглядно смоделирован и разрешён (не обойдён удалением истории) |
| Remote | Проект доступен на GitHub/GitLab; push выполнен |
| README | Постановка + ФИО/инициалы + пошаговые команды и описание конфликта |
| Аккуратность | Понятные сообщения коммитов, итоговый проект в согласованном состоянии |
